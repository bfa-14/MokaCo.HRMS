## How the comparison was made

`docs/payroll_run_compare.sql -v RunId=17 OnlyFixes=1 RateType=Own`: inside one rolled-back transaction the run's rate row is re-snapshotted at full precision from the same source row it froze, the lock side-effects are undone for the regeneration only (adjustments consumed by run 17 made payable again, expenses un-stamped), data that appeared **after the lock** is set aside so it is not mistaken for a fix effect (1 employee hired since — Bilal, 1 termination date set since — Joe Abou Jaoude, 2 separations prepared since — Hadi Rammal and Joe Abou Jaoude, 4 attendance records processed since — all Hadi Rammal, 14–19 Aug), the run is marked Draft inside the transaction and `payroll.usp_PayrollRun_Generate` (fixed) is executed, then everything is rolled back.

## Settling the differences (for HR)

1. In `PAYROLL_ADJUSTMENT` (Payroll › Adjustments, target period 2026-08) raise one request per employee for the **Diff USD** above — a deduction where negative (extra NSSF employee share + income tax that should have been withheld), an earning where positive. Use the NSSF Employee Share / Income Tax component types so the statutory report picks them up; the employer-share differences are a company-side correction to the NSSF declaration and are not paid through payslips.
2. Create the supplemental (`POST /api/payroll/runs` with `runType: "Supplemental"`, or leave it out for a primary — a missing type is a primary run since BUG-18), generate, review, approve. The rate frozen into the new run will be stored at full precision (BUG-07).
3. Do not unlock run 17. Its rate row still reads 0.000000000000 by design: a locked run is never altered; this document is its correction trail.
