# Payroll & Attendance System — Design Diagrams

Target stack: **SQL Server 2025 · .NET Core APIs · React + DevExtreme**
Context: single coffee shop (branch-aware), dual currency **USD/LBP**, fingerprint device **HTTP push**.

These diagrams are the blueprint for Phase 1–3. They are intentionally not exhaustive on every column — they fix the *shape* of the system (entities, boundaries, and the tricky data flows) so implementation has a stable target.

---

## 1. System Architecture

The key boundary: the **device's contract is messy and untrusted**, so it is isolated behind a proxy and an immutable raw-log table. Everything domain-related happens *after* ingestion, in a separate processing layer.

```mermaid

        AGENT["Optional Middleware Agent<br/>normalizes to JSON over HTTPS"]

    subgraph Edge["Network Edge"]
        RP["Reverse Proxy<br/>TLS · IP allowlist · VPN"]
    end

    subgraph Backend[".NET Core Backend"]

        CORE["Core Application Services<br/>Employee · Shift/Roster · Leave<br/>Exit Permits · Payroll Engine · Currency"]
```

## 4. Punch Ingestion — Sequence

Covers the three realities of HTTP-push devices: **idempotency** (resends), **offline buffering** (back-dated punches), and the **command channel** (time-sync to prevent clock drift). Pairing and anomaly handling are async, never inline with ingestion.

```mermaid
sequenceDiagram
    participant D as Fingerprint Device
    participant P as Reverse Proxy
    participant I as Ingestion API
    participant R as RawDeviceLog
    participant J as Background Job
    participant DB as SQL Server

    Note over D: Employee scans finger
    D->>P: HTTP POST punch(es)
    P->>I: forward (TLS, allowlisted)
    I->>I: validate + build dedup hash
    alt new punch
        I->>R: insert raw log
    else duplicate
        I-->>R: skip (idempotent)
    end
    I-->>D: ACK

    Note over D,I: Device may buffer offline,<br/>then resend back-dated punches

    loop scheduled
        J->>R: fetch unprocessed logs
        J->>DB: map EnrollPin to Employee
        alt unknown PIN
            J->>DB: queue for manual mapping
        else mapped
            J->>J: pair in/out vs shift assignment
            J->>J: compute late / overtime
            alt clean
                J->>DB: upsert AttendanceRecord
            else anomaly (odd punches, no out)
                J->>DB: flag for correction workflow
            end
        end
        J->>R: mark processed
    end

    Note over D,J: Command channel
    D->>I: poll for commands
    I-->>D: time-sync / enroll updates
```

## 5. Payroll Run — Flow & Lifecycle

A run gathers all inputs per employee, **snapshots the exchange rate**, computes per-currency lines, then moves through draft → review → approved → **locked**. Once locked it is immutable; later fixes become adjustments in the *next* period.

```mermaid
flowchart TB
    START([HR starts payroll run for period]) --> GATHER[ ]

    subgraph Inputs["Gather inputs (per employee)"]
        ATT["Attendance<br/>late · absence · OT"]
        LV["Leave & exit permissions<br/>paid vs unpaid"]
        SC["Salary components<br/>basic · allowances · deductions"]
        ADV["Advance installments due"]
        BON["Ad-hoc titles<br/>e.g. monthly bonus"]
    end

    GATHER --> Inputs
    Inputs --> RATE{"Snapshot USD-LBP<br/>rate(s) for period"}
    RATE --> CALC["Payroll Engine<br/>per-currency lines<br/>decimal · fixed rounding"]
    CALC --> DRAFT[["Draft payslips<br/>NetUSD + NetLBP"]]

    DRAFT --> REVIEW{Review}
    REVIEW -->|rejected| ADJUST["Adjust components / corrections"]
    ADJUST --> CALC
    REVIEW -->|approved| LOCK[["Approve & LOCK run<br/>rate snapshot frozen"]]
    LOCK --> OUT[ ]

    subgraph OUT2["Outputs"]
        PAYSLIP["Print payslips"]
        BANK["Bank / cash transfer sheet"]
        REPORTS["NSSF & summary reports"]
    end

    LOCK --> OUT2
    LOCK -.locked = immutable.-> NEXT["Corrections go to next period<br/>as adjustments"]
```

## How these map to the build phases

- **Phase 1 (MVP):** Diagrams 1, 2, 4 — RBAC, employee master, shifts/roster, ingestion, pairing, late/absence.
- **Phase 2:** Leave + exit-permission entities from diagram 3, with approval workflows.
- **Phase 3:** Payroll/currency entities from diagram 3 and the full flow in diagram 5.
- **Phase 4:** Self-service portal, dashboards, documents, notifications.

Two things still to confirm before schema implementation (they only affect detail, not shape): the **exact device model/firmware** (sets the real ingestion payload), and the **NSSF/official-rate treatment** with your accountant (regulatory, not a design choice I should make).
